feat(api): implement Referral, Attachment, and Notification modules

- Add referrals table with three distinct RLS policies (SELECT visible to
  either side, INSERT only by origin, UPDATE only by destination) - the
  one table where two different tenants legitimately share one row
- Add POST /referrals (frozen snapshot at send time), GET /referrals/outgoing,
  GET /referrals/incoming, POST /referrals/:id/claim (always creates a new
  Patient in the destination facility, never merges)
- Add attachments table plus local-disk upload (initiate/upload/retrieve),
  clearly documented as a stand-in for real S3 plus per-facility KMS
- Add notifications table (pull-model, tolerant of offline recipients)
  and wire the escalation sweep to actually notify ward_head/director
  users per facility instead of just logging
- Fix a real bug in referral claiming: TypeORM repo.save() does not verify
  an UPDATE actually affected a row, so an RLS-blocked claim attempt
  (origin trying to claim its own referral) silently succeeded in
  application code while doing nothing in the database, and worse,
  created an orphaned Patient record before the no-op update was even
  attempted. Fixed by using a raw UPDATE...RETURNING and checking the
  actual row count before creating anything.
- Fix a second, related bug found while fixing the first: queryRunner
  query() returns a rows-plus-affectedCount tuple for non-SELECT
  statements, not just the rows array. Treating the tuple as the rows
  array made the zero-rows check never trigger and silently corrupted
  the resolved value with undefined fields instead.
- Verified end-to-end: referral sent, origin correctly blocked (403) from
  claiming its own referral with no orphan patient left behind,
  destination claims successfully with provenance preserved, re-claiming
  rejected (400); attachment initiate, upload, metadata, and byte-for-byte
  retrieval all verified; escalation sweep confirmed to create a real
  notification for a ward_head user where none existed before
